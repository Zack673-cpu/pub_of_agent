# 第一部分 功能设计

这一部分只讲功能：用户做什么、系统怎么反应。不涉及任何代码、模型、接口。

## 一、整体骨架

- 前端两个页面：**写作页**、**历史记录页**。
- **左侧栏**可收缩，里面就两个入口切换这两页；「写作」旁边还有一个 **+ 新建**，用来开第二本书。
- **界面上不出现任何对话记录**。用户在输入框打的指令，发出去就消失，不留痕、不显示（详见 §六）。
- 写作页比历史页多一个**右侧栏**，显示小节正文。

## 二、写作页

### 2.1 两种状态

| 状态 | 页面长什么样 |
|---|---|
| 没有正在写的书 | 一张新建表单：**书名**、**大致要求**、「开始生成大纲」按钮。书名和要求分两个框，因为书名要单独拿去做历史记录搜索 |
| 有正在写的书 | **AI 显示区**（含输入框）+ **右侧栏** |

### 2.2 AI 显示区：三截

从上到下就三截，没有对话记录那一截。

#### 第一截：大纲块

- **钉死在显示区底部**，紧贴固定提示行上方。
- **永远只显示最新一份大纲**。AI 改完、用户手动改完，都是**原地刷新覆盖**，旧大纲一律不显示（要看旧版得点右上角箭头往回切）。
- 大纲块**不是只读的**，下面这些功能全在这个块里做：
  - 每个节点是个小框，框边有加号、减号，可以加子节点、删节点
  - 可以改节点标题、调层级（升一级/降一级）、调顺序（上移/下移）
  - 改完**失焦自动暂存**，或 **Ctrl+S** 暂存
  - 右上角有**自己的后退/前进箭头**（切大纲版本）
  - 可以**左键拖动选中节点加进输入框当索引块**
  - **点任意一节 → 右侧栏换成对应那一节的正文**（大纲块和右侧栏一一对应）
- 块内顶部有**一行状态提示**，没事的时候不显示，有事才显示：

| 提示文字 | 什么时候出现 |
|---|---|
| `请等待` | 大纲正在生成 |
| `正在写第 3 节，共 18 节` | 整本初稿生成中 |
| `生成完成` | 任务结束 |
| `第 7 节生成失败` | 某一节写崩了 |

- **提交按钮不在这里**（提交只在右侧栏）。

#### 第二截：固定提示行

- 一行字 + 一个「生成初稿」按钮。
- 这行字**由程序写死，不是 LLM 生成的**。
- **只在检测到大纲有改动时才出现**，不是常驻：

| 什么时候 | 提示行 |
|---|---|
| AI 首次生成完大纲 | **出现** |
| AI 按用户要求改完大纲 | **出现** |
| 用户在大纲块里手动改了并暂存 | **出现** |
| 点了「生成初稿」 | **消失** |
| 之后大纲又被改动（AI 改或手动改） | **重新出现** |

#### 第三截：输入框

打字 + 放索引块。详见 2.4。

### 2.3 右侧栏

- **只有当前选中那一节的正文，没有大纲树**（大纲在显示区已经有了，不重复显示）。
- 右上角三个东西：**后退箭头**、**前进箭头**、**提交**。
- 几种特殊显示：

| 情况 | 右侧栏显示 |
|---|---|
| 这一节还没生成过 | `尚未生成初稿` |
| 这一节生成失败了 | `生成失败` + 一个「重试本节」按钮 |
| 选中的是大纲里新加的空节点 | `尚未生成`，同时输入框上方给一句提示，告诉用户输要求就能单独生成这一节 |

- **哪一节有暂存但没提交的改动，就在大纲块对应那个节点上打一个小标记**，让用户知道哪几节动过。

### 2.4 输入框怎么判断这条指令是干什么

**由 AI 判断，不靠界面状态硬猜。**

（这一条是本轮修正的结果。原先设计的是「靠有没有索引块 + 当前选中什么来硬判定」，作废——因为用户随手输入的一句话可能是改大纲也可能是改正文，靠界面状态猜不出来。）

用户发一条指令，系统把它**连同当前这本书的状态**（最新大纲、各节正文、哪些节是空的）一起交给 AI，AI 判出意图：

| AI 判断结果 | 系统怎么做 | 要不要先问一句 |
|---|---|---|
| 改大纲 | 拿「用户的要求 + 最新大纲」去改大纲 | **如果这次改动会导致某几节已写好的正文被清空 → 先弹确认**：「这条会改动大纲，第 X 节、第 Y 节已写好的正文会被清空，确定吗」；不会清空就直接执行 |
| 重写正文某处 | 只重写那部分正文 | 直接执行 |
| 给某个空节生成正文 | 单独生成那一节 | 直接执行 |
| 确认大纲、开始生成整本 | 走整本生成 | 直接执行 |
| 认不出用户到底指哪 | **不瞎猜**，提示用户说清楚 | — |

**索引块的角色**：它**不是判定依据，是给 AI 的定位锚点**。

- 有索引块 → AI 精确知道用户说的是哪一段、哪个节点
- 没索引块 → AI 从文字里推断（用户说「第三章第二节讲得太浅」，AI 自己去对大纲节点）；推断不出来就走「认不出」那条

**为什么要加那道安全闸**：AI 判断有概率出错。判错「重写正文」顶多改得不好，用户还能改回来；判错「改大纲」会直接清掉已写好的正文，不可逆。所以只在不可逆的那条上加闸。

**索引块本身的交互**：

- 大纲块和正文的索引块**长得一样，可以混在同一个输入框里一起发**
- 每个块是个特殊方框，**只显示选中内容的开头几个字**
- **鼠标指向方框左上角的 ×，点一下就取消这个选中**
- 发送时如果混放了，**执行顺序是先大纲后正文**
- **冲突保护**：发送前如果检测到「用户要重写的正文片段，所在那一节会因为这次大纲改动被清空」，**弹提示告知哪几个片段会白做**，用户确认了才继续
- **加了索引块之后又去改了正文或大纲 → 索引块失效**（内容已经变了，锚点对不上）

**其他两条**：

- **「生成初稿」按钮保留**，作为零歧义的快捷方式：点按钮 = 直接确认，不经 AI 判断。
- **AI 生成期间输入框禁用**（正在干活，不许插话）。

### 2.5 从零写一本新书

| 步 | 用户做什么 | 系统怎么反应 |
|---|---|---|
| 1 | 左侧栏点「+ 新建」，填书名 + 大致要求，点「开始生成大纲」 | 大纲块顶部状态行显示 `请等待`，输入框禁用 |
| 2 | 等 | 大纲生成完 → 显示在大纲块 → 固定提示行出现 → 状态行消失 |
| 3 | 觉得不满意，在输入框提修改要求，发送 | AI 拿「要求 + 最新大纲」改 → 大纲块**原地刷新** → 提示行还在 |
| 4 | 第 3 步可以循环任意多次 | 同上 |
| 5 | 满意了，点「生成初稿」 | 提示行消失 → 状态行显示 `正在写第 N 节，共 M 节` → 输入框禁用 → 一节一节串行写 |
| 6 | 等写完 | 状态行显示 `生成完成` → 右侧栏默认显示**第一节** → 点大纲块任意一节，右侧栏换成对应那节 |

大纲这一路**只记忆最新的一份**，不会把历史大纲全塞进上下文撑爆。

### 2.6 四种改法

#### 改法一：在输入框说大纲要改

AI 改完大纲后，**按节计算后果**：

| 大纲这次的改动 | 对应那一节的正文怎么办 |
|---|---|
| 新加了一节 | 变成**空节点**，右侧栏显示「尚未生成」；用户选中它、输入要求，AI 就单独给这一节生成正文 |
| 删掉了一节 | 那一节**连正文一起丢弃** |
| 改了某节标题 | 那一节**旧正文按需保留**；提了要求就按要求重写，没提AI就按照意思看看是局部重写或者不用修改或者全部重写 |
| 没动的节 | **原样保留，不重写** |

#### 改法二：直接在大纲块里动手

用 2.2 说的结构化树编辑器改（加节点、删节点、改标题、调层级、调顺序），失焦或 Ctrl+S 暂存。
如果是手动修改的大纲，用户没有提要求重写就不动那一节正文，其余后果**和改法一那张表完全一样**。

#### 改法三：选中一小段让 AI 重写

| 步 | 用户做什么 | 系统怎么反应 |
|---|---|---|
| 1 | 在右侧栏**左键长按拖动**选中一段正文 | 选区高亮 |
| 2 | 松开左键 | 选区旁边**浮出一个「添加到会话」按钮** |
| 3 | 点这个按钮 | 输入框里出现一个**索引块**：特殊方框包裹，只显示这段的开头几个字 |
| 4 | 不想要了 | 鼠标指向方框**左上角的 ×**，点一下取消 |
| 5 | 输入重写要求，发送 | 只把**这一小节**送去重写 |
| 6 | 等 | AI 拿到「这一小节全文 + 用户的要求 + 哪些句子是用户手改过的」去重写 |
| 7 | 看完 | 重写结果替换回该节，进暂存（还没提交） |

**重写范围不给硬边界**——不是死板地只替换选中的那几个字，AI 自己根据语境判断该改多大范围，保证句子通顺。但提示词里明确要求：**不许改用户手改过的内容；如果根据语境一定要改，必须保住用户改过那句的原意**。

#### 改法四：自己直接改正文

| 用户做什么 | 系统怎么反应 |
|---|---|
| 点右侧栏内容区 | 从「看的样子」切成「改的样子」：彩色标记消失，变成干净可编辑框，光标落在点的位置 |
| 改完，点别处（失焦）或按 Ctrl+S | 存暂存 → 切回「看的样子」→ 显示三色改动标记 |

### 2.7 版本规则（大纲和正文都一样）

参考 git 的思路：**版本是一条直线，不分叉**。

| 问题 | 规则 |
|---|---|
| 版本链什么形状 | 一条直线，不分叉 |
| 什么才算产生了一个新版本 | **只有「提交」产生新版本**。暂存（失焦 / Ctrl+S）**不算版本** |
| 能在哪个版本上改 | **只能在最新版上改** |
| 后退箭头 | 切到更早的版本，**只读，不能打字** |
| 前进箭头 | 往回切到更新的版本 |
| 保留多少个 | **只保留最近 5 个已提交版本**（含当前最新，也就是最多能后退 4 步） |
| 到头了 | 箭头**变灰，点击无反应** |
| 就是想改旧版 | 切到那一版 → 点「**以此版为准继续修改**」→ 弹确认「舍弃之后 N 个版本，确定吗」→ 确认后**这一版变成最新版，后面的全砍掉** |
| 被砍掉的版本，它产生的语料怎么办 | **保留**。语料对照资料不跟着版本一起删 |
| 切版本的时候 | **自动滚到这一版第一处改动的地方，高亮闪一下** |

### 2.8 改动标记

- 所有改动处**都加下划线**
- **绿色 = 增加**
- **黄色 = 修改**
- **红色小三角 = 删除**，插在两个文字下面，**不占下一行**；鼠标悬停能看删了什么
- 比什么和什么：

| 什么时候 | 比法 |
|---|---|
| 平时（在最新版上） | 「现在看到的内容（含暂存改动）」vs「最新提交版」 |
| 切到旧版看的时候 | 「那一版」vs「它的前一版」 |

**大纲块上同一套标记**：新加节点绿、删掉节点红三角（塞在节点标题下方不占新行）、标题改过黄，都带下划线；比法也一样。

### 2.9 「看」和「改」两种样子

这是**和切版本分开的另一件事**——切版本是换内容，看/改是换交互形态。

| 用户做什么 | 系统怎么反应 |
|---|---|
| 什么都不点 | 就是**看的样子**：带彩色改动标记，不能打字 |
| 点内容区任意处 | 切成**改的样子**：彩色标记消失，变干净可编辑框，光标落在点的位置 |
| 改的样子下失焦 或 Ctrl+S | 存暂存 → 切回**看的样子** → 重新显示三色标记 |
| 点后退/前进箭头 | 切版本，**看的样子 + 只读**，自动滚到第一处改动高亮闪一下 |

**大纲块完全同样适用这四条**：切版本自动对焦到第一处改动的节点、三色标记、看/改两态切换、比法一致。历史页左半的大纲树也一样。

### 2.10 提交

- 「提交」按钮**只在右侧栏右上角**（大纲块上没有）。
- 点了弹一句：**「将要清空暂存区，确定提交吗」**。
- **整本一次提交**：大纲 + 所有节的正文，一起提交。
- 提交之后：暂存区清空 → 产生新版本 → 语料落库 → 这本书变成已提交状态 → 历史记录里出现/更新这个书名。
- 不满意可以**无限循环**接着改。
- 「提交」现在其实只是清空暂存区、把内容变成终稿，因为还不知道要提交到哪个真实系统去——**但这句解释不写在页面上**。

## 三、历史记录页

### 3.1 列表

- 一进去是**缩成一行行的记录概要**，概要**只显示书名**。
- 上面一个**搜索栏，按书名搜**。
- **最近改过的排最上面**。

### 3.2 详情

点一条概要进去，**两部分占满整页**：

| 位置 | 内容 |
|---|---|
| 左半 | **大纲树**，可编辑（增删改节点、调层级调顺序），失焦/Ctrl+S 暂存，右上角有自己的后退/前进箭头，全套 2.7~2.9 规则 |
| 右半 | **正文，默认显示第一节**；点左半任意一节，右半换对应那节；右上角后退/前进/**提交修改** |

- 编辑行为和写作页**完全一致**：暂存、三色标记、版本前进后退、看/改两态、自动对焦。
- **页面底部也有输入框**，可以下指令让 AI 改，同样**不留痕**。
- 点「提交修改」→ 弹「确定吗」→ 清空暂存区 → **同步更新这条历史记录**（不是新增一条）。
- **整个流程都在这页里闭环完成**，不用跳出去。

### 3.3 「让 AI 修改」

- 按钮在**详情页顶部**，只有**已提交状态**的书才出现。
- 点了之后**切换到写作页**：AI 显示区就是这本书记录的那个大纲，右侧栏是已经写好的所有小节、默认第一节、一一对应。
- 之后就走写作页那一整套修改流程。
- 最后提交修改 → 清空暂存 → **同步回历史记录**。
- **两页共用同一份暂存数据**：在历史页改了一半没提交就点「让 AI 修改」跳到写作页，那半截改动不会丢。

## 四、权限

按台账第 27 项的角色权限走：

| 角色 | 能看什么 | 额外能用什么 |
|---|---|---|
| 普通编辑 | **只看自己的书** | — |
| 高级编辑 / 管理员 | **看全部人的书** | 微调入口、语料入库 |

## 五、语料只收三类

| 类型 | 什么时候产生 |
|---|---|
| **用户问题 → 大纲** | 用户提大纲修改要求，AI 返回新大纲 |
| **用户问题 → 正文小节** | 局部重写：用户的重写指令 → AI 重写后的片段 |
| **AI 正文小节 → 人工定稿** | 用户手改正文之后提交 |

- **不收**：对话过程、AI 的闲聊回复、AI 的思考过程。
- **只在「提交」那一刻收**，暂存不收（暂存频率太高，会攒出一堆半成品垃圾对，稀释语料质量）。
- 局部重写那条**要进语料**（设计过程中曾判它不进，已修正——它正好符合「用户问题 → 正文小节」）。

## 六、下线项与两个默认

- **原有的自由问答功能下线**。那是阶段一手写 RAG 一路留下来的（输入框问什么答什么），现在输入框只用来下指令、界面上也不显示对话，所以它没地方待了。已在台账第 33 项销账里记一笔。
- 两个用户没明说、按最省事方式定的默认：
  1. 「+ 新建」按钮放在左侧栏「写作」旁边
  2. AI 生成期间输入框禁用

# 第二部分 代码细节

## 七、三个核心问题的技术裁定

### 7.1 前后知识联动怎么解决

**问题**：一节一节写，模型看不到前面写过什么，会出三种病——重复解释已经定义过的概念、术语前后不统一、该呼应的地方不呼应。

**解法**：不注入全文，注入**压缩骨架**四件套：

| 注入项 | 内容 | 体量 |
|---|---|---|
| 全书大纲 | 完整节树 | 几百字，固定 |
| **滚动摘要卡** | 每写完一节，让模型产一张约 150 字的卡：讲了什么概念、下过什么定义、留了什么伏笔 | 20 节的书约 3000 字 |
| **累积术语表** | 术语 → 一句话定义 → 首次出现在第几节 | 随节数增长 |
| 前一节尾段原文 | 上一节最后 200~300 字 | 固定 |

模型上下文 128k，这个量级完全够。

**最小版不做「节级前置依赖标注」**（显式标出「第 5 节依赖第 2 节」），列 P1 待办，等书的节数超过 50 再上。全书层面的术语统一 / 重复检查交给**新增第 35 项「全书一致性终审 Agent」**。

### 7.2 初稿生成是一节一节还是整本

**对用户是整本一次生成**（一个按钮，没有选节环节）；**对模型是一节一节串行生成**。

**禁止整本一次吐**，三个硬理由：

1. **输出长度顶不住**：单次输出约 8k token，教材几十万字必被截断
2. **失败爆炸半径大**：第 15 节崩了整本重来
3. **超长文本后半段注意力衰减**，反而更失控

**串行不并行**（并行写第 5 节时看不到第 4 节，联动就废了）。「按章并行、章内串行」列 P1 待办。

**硬约束**：18 节 × 每节最多 5 轮审校 = 上百次模型调用，实测 5~15 分钟，**同步 HTTP 必超时**。所以长任务机制从「靠后的承压项」变成**硬前置**。

### 7.3 编辑改写对在哪些步骤存、存什么

**五个产生点**：大纲修订 / 局部重写 / 写作页手改提交 / 历史页手改提交 / 「让 AI 修改」回流后提交。

**三条焊死规则**：

1. **只在「提交」那一刻写库，暂存不写**。理由见 §五。
2. **粗粒度对由版本链派生，不另存**（有 `draft_versions` 就能算出「AI 原文 → 人工定稿」）；**细粒度改动块必须抽出来单独存**，含前后各 50 字的上下文窗口。
3. **diff 后端只算一份**：页面上的三色标记和语料里的 `diff_ops_json` 用的是**同一份计算结果**，禁止前后端各写一套。否则会出「页面显示改了这里、语料存的是改了那里」，微调数据全废。

### node_key 怎么保持稳定

大纲变更后节还能一一对应，靠的是 `sections.node_key`，**不是位置也不是标题**。

- **人工编辑**走结构化树编辑器 → node_key 天然稳定（改标题不换 key）
- **AI 修订**走标题序列对齐：`difflib.SequenceMatcher` 比新旧标题序列，`equal` 的沿用旧 key，`replace` / `insert` 的分配新 key

一个巧合让这事变简单：**对齐误判的后果恰好等于要求的行为**。如果标题改得太多被算法判成「新节点」，那旧内容就被丢弃——正好就是「修改即丢弃」。所以不需要做精密匹配。

### 作废初稿的物理语义按书状态分流

| 书的状态 | 作废的正文怎么处理 |
|---|---|
| `drafting`（从未提交过） | **物理丢弃**，按用户原话「不进任何数据库」 |
| `submitted`（已提交过） | **标记 `discarded=true`**，前端不显示，但语料和诊断数据保留（已提交的书，它的 `edit_pairs` 已经有语料价值） |

## 十一、前端技术裁定

| # | 裁定 | 理由 |
|---|---|---|
| 1 | **前端改用 Vite 工程**（Vue3 + Element Plus + Vue Router + Pinia），不再用 CDN 单文件 | 组件量和状态复杂度已经超了单 HTML 能扛的范围 |
| 2 | **diff 后端算一份**，前端只渲染 | 见 7.3 规则 3 |
| 3 | **渲染态 ⇄ 编辑态切换**，不用 `contenteditable`，不用双层叠加 | `contenteditable` 有光标管理、粘贴污染、中文输入法三个坑；双层叠加有滚动同步、输入法、折行对齐三个坑；态切换天然契合「失焦自动暂存」 |
| 4 | **暂存放服务端 MySQL**，不放 localStorage | 多用户隔离、换设备不丢、diff 必须在后端算 |
| 5 | **版本链只保留最近 5 个已提交版本** | 见 2.7 |
| 6 | **整本串行生成**，不按章并行 | 见 7.2 |
| 7 | **长任务 = MySQL `tasks` 表 + 后台串行 + SSE 只推进度事件**（不推正文流）+ `task_id` 断线恢复 | 契合「只显示请等待」的要求 |
| 8 | **公式渲染本轮不做** | MathJax 重排版 DOM 会打乱字符 offset，和局部重写、三色 diff 直接冲突；延续模块 7 已生效的「初稿禁公式」 |
| 9 | **查重报告本轮不在界面展示** | `check_duplicate` 照跑，只是不给 UI |
